# Focused paths beat whole-system code maps

Research and practice agree on one point. A code map helps a reader when it answers the question in front of them, and it fails when it tries to show everything. Developers ask path questions ("how does control get from A to B?") and rationale questions ("why does this exist?") far more often than structure questions. These path and rationale questions also cause the most difficulty. Tools that show a **working set or a call path on one canvas** produced the measured gains: Code Bubbles users finished tasks **33% faster**, and Reacher users succeeded **over 5 times more often** on control-flow questions. Large whole-system maps went unused, except by new hires during onboarding. Sourcetrail tried a whole-codebase graph first and abandoned it for a one-symbol ego view. The design consequences for a Go documentation map follow directly. Make a focus view with a budget of about 20 nodes the main work surface. Lay out callers left and callees right, and group the neighbours by relation type. Label every edge with a verb. Use semantic zoom that redesigns each level, and do not only scale it. Give every focus state a URL and a breadcrumb. Put "About …" explanations and guided tours beside the reference facts, not inside them. Encode every relation with line pattern and text as well as an Okabe–Ito hue. The evidence base has gaps. No controlled study isolates semantic zoom for code. No study compares ego views with whole graphs for code. The 20-node budget comes from general graph-reading studies.

## Developers ask about paths and reasons, not boxes

The classic comprehension models describe different strategies. Brooks describes top-down reading with beacons. Pennington describes bottom-up chunking. Letovsky describes opportunistic inquiry episodes. They agree on one conclusion: developers switch strategy constantly and read only what the task needs. Storey, Wong and Müller studied 30 participants. They concluded that tools should "provide ways to easily enter and effortlessly switch between strategies" and should not impose one strategy ([Storey et al.](https://www.st.cs.uni-saarland.de/edu/empirical-se/2006/PDFs/storey98.pdf)). Littman's "as-needed" strategy dominates in large programs. It also misses interactions between parts and leads to more mistakes.

Field studies show which questions hurt. LaToza and Myers surveyed **460 professionals**. These developers asked reachability questions **more than 9 times a day**. In a field study, **9 of the 10 longest activities** involved reachability questions. "What are the implications of this change?" ranked as both the most frequent and the hardest question. Only 16% found the structural question "How are instances created and assembled?" hard. Experience in the codebase did not make the hard questions easier ([LaToza & Myers 2010](https://memphis-cs.github.io/comp-7085-8085-2012-fall/papers/LaToza2010ICSE.pdf)). Sillito, Murphy and De Volder sorted 44 question types into four steps (see [the UBC record](https://open.library.ubc.ca/collections/831/items/1.0052042)):

1. Find a focus point.
2. Expand from that point.
3. Understand a subgraph.
4. Compare groups of subgraphs.

A focus-based map supports each step directly. LaToza and Myers estimate that **52% of Sillito's poorly supported questions** concern reachability ([LaToza & Myers 2010](https://memphis-cs.github.io/comp-7085-8085-2012-fall/papers/LaToza2010ICSE.pdf)).

Rationale forms the second gap. Ko, DeLine and Venolia observed 17 Microsoft developers. "Why was this code implemented this way?" ranked among the most often unsatisfied needs, because the only source sat in an unavailable coworker's head ([Ko et al. 2007](https://faculty.washington.edu/ajko/papers/Ko2007InformationNeeds.pdf)). Roehm et al. studied 28 professionals. **21 of them trusted source code and inline comments more than documentation**, and none used state-of-the-art comprehension tools ([Roehm et al. 2012](https://memphis-cs.github.io/comp-7085-8085-2012-fall/papers/Roehm2012ICSE.pdf)). LaToza recommends rationale that stays "bidirectionally connected to the code" ([LaToza 2020](https://people.cs.gmu.edu/~tlatoza/papers/InformationNeeds-LessonsForProgrammingTools.pdf)). For a Go map, this points to godoc comments and linked design records. A separate prose site does not meet the need.

Information foraging theory explains how readers choose where to go. Developers follow "scent". Scent means the word similarity between their goal and the proximal cues in identifiers, comments and labels. A model built on scent and link topology predicted navigation better than models built on hypotheses ([Lawrance et al. 2013](https://web.engr.oregonstate.edu/~burnett/Reprints/TSE-IFT-2013-asprinted.pdf)). Every label on the map therefore acts as a navigation cue. Terse Go names such as `svc` or `repo` give weak scent. The godoc first sentence beside each name gives strong scent at almost no cost. In SHriMP, subsystem naming proved "critical": one misleading region name sent users to the wrong place ([Storey et al.](https://www.st.cs.uni-saarland.de/edu/empirical-se/2006/PDFs/storey98.pdf)).

## Working sets win and wall-sized maps go unused

The measured successes share one pattern. They show the task's slice of the code together. **Code Bubbles** puts single methods into bubbles on a canvas. In a study with 20 participants, its users finished tasks 33.2% faster. Their navigation time fell from **11.6 to 3.5 minutes** ([Bragdon et al. 2010](https://www.cs.ucf.edu/~jjl/pubs/p2503-bragdon.pdf)). **Debugger Canvas** shipped this idea inside Visual Studio. Interviewees most often valued it for "debugging long and complicated call paths" and for unfamiliar code laid out "to reflect the call paths rather than file organization" ([DeLine et al. 2012](https://microsoft.com/en-us/research/wp-content/uploads/2016/02/p1064-213-deline.pdf)). **Reacher** lets developers search along a call graph instead of walking it by hand. Its users succeeded over 5 times more often, in less time, and stayed oriented ([LaToza & Myers 2011](https://people.cs.gmu.edu/~tlatoza/papers/vlhcc2011.pdf)).

The failures share the opposite pattern. A Microsoft team co-designed a large, stable code map and hung it on a wall for a month. It saw "little evidence of interaction". Readers found "too few or too many details" for the discussion at hand. Only two new hires used their copies, for onboarding ([Cherubini et al. 2007](https://microsoft.com/en-us/research/wp-content/uploads/2016/02/codemap_vlhcc07.pdf)). Sourcetrail's early prototypes showed the whole codebase and failed. The product then showed one active symbol with its direct relationships ([TheServerSide](https://www.theserverside.com/feature/New-IDE-tools-to-visualize-code-may-accelerate-app-dev/)). SHriMP offered fisheye distortion, but users preferred to zoom in for detail and zoom out for context ([Storey et al.](https://www.st.cs.uni-saarland.de/edu/empirical-se/2006/PDFs/storey98.pdf)). The overview still has a role. Users zoomed out "when a user paused to rethink a strategy". New hires used the overview to orient. The overview therefore serves reorientation and should not serve as the main work surface.

Degree-of-interest (DOI) research says how to choose what a focus view shows. Van Ham and Perer combine a-priori importance, graph distance from the focus and the user's search context. From these they compute **a connected subgraph of at most S nodes** with maximal total interest. They expand in steps of the top N neighbours and never add all neighbours at once. They show a count of hidden neighbours on each node. They highlight fewer than 5 "directions for expansion". Without DOI, two hops from one focus produced 2,345 nodes ([van Ham & Perer 2009](https://perer.org/papers/adamPerer-DOIGraphs-InfoVis2009.pdf)). Graph-reading studies favour node-link diagrams at about **20 nodes** and find the advantage weaker at 50. Path finding remains the one task where node-link consistently wins ([Okoe et al. 2018](https://smsf.cs.arizona.edu/~kobourov/NL-AM-TVCG18.pdf); [Ren et al.](https://www.cambridge.org/core/journals/network-science/article/understanding-nodelink-and-matrix-visualizations-of-networks-a-largescale-online-experiment/C293136C4761F09D4C2C328E2BC19287)). Treat the 20-node figure as a starting budget. No study has measured an optimal size for code ego views.

Metrics belong elsewhere. SHriMP users complained most about "the large number of visible arcs" and asked for arcs hidden by default and shown on request ([Storey et al.](https://www.st.cs.uni-saarland.de/edu/empirical-se/2006/PDFs/storey98.pdf)). CodeCity's metric city improved correctness on its tasks ([ICSE 2011](https://2011.icse-conferences.org/content/software-systems-cities-controlled-experiment.html)). Those gains do not obviously transfer to "what does this do?" questions. A count badge such as "12 callers" serves navigation. Node size by lines of code does not.

## Storey's elements, C4 notation and Sourcetrail set the grammar

Storey, Fracchia and Müller list 14 cognitive design elements ([SFM 1999](https://plg.uwaterloo.ca/~migod/846/papers/storey-jss.pdf)). Most of them map onto map features. **E1** asks for visible syntactic and semantic relations. **E3** asks for user-built abstractions, because maintainers trust groupings they made over "prefabricated" ones. **E5** asks for overviews at several levels. **E7** asks for linked views that highlight the same object everywhere. **E8 and E9** ask for directional navigation along calls, plus bookmarks and search. **E10 to E12** ask the tool to show the current focus, the path that led there, and the options for the next step. **E13** asks for animated, continuous transitions. Doc tools rarely support E3 and E11. E11 includes recording *why* the user looks at an object.

C4 supplies notation rules that fit a documentation map with no changes ([C4 notation](https://c4model.com/diagrams/notation)). Every diagram has a title and a key. Every element states its type, a short responsibility description and a technology. Every line stays unidirectional and carries a specific label. C4 bans vague labels such as "Uses". C4 also has one diagram per zoom level ([c4model.com](https://c4model.com/)). Structurizr **dynamic views** add ordered, titled flows on top of the static model. The flows live in these views, so the static model needs fewer edges ([Structurizr](https://docs.structurizr.com/dsl/cookbook/dynamic-view/)). The mapping to Go works as follows: a region acts as a container, a package acts as a component, and types and functions form the code level.

Sourcetrail's documentation gives the most complete interaction grammar for an ego graph ([Sourcetrail docs](https://github.com/CoatiSoftware/Sourcetrail/blob/master/DOCUMENTATION.md)). It has these features:

1. Bundle nodes with counts replace large sibling sets.
2. Members sit inside their type, collapsed, with a count.
3. Edge thickness shows multiplicity.
4. A click on an edge shows the call-site snippets.
5. "To Target Symbol" trails answer "how does A reach B?".
6. A depth slider makes more than one hop an explicit choice.
7. Back and forward history and bookmarks support return.
8. A legend sits behind a `?` button.

pkg.go.dev supplies the Go-native layout for the package level. Its Index nests constructors and methods under each type. It shows Imports and Imported By with counts. It uses the first doc sentence as a summary ([pkg.go.dev/net/http](https://pkg.go.dev/net/http); [pkgsite about](https://pkg.go.dev/about)). Sourcegraph groups a symbol's relations into separate, counted panels: definitions, references and implementations. It truncates long lists instead of drawing them ([Sourcegraph docs](https://sourcegraph.com/docs/code-navigation)).

Semantic zoom means each level gets its own rendering, "based on various semantic and task considerations", and not plain geometric scaling ([Bederson & Hollan 1994](https://www.lri.fr/~mbl/Teach/SituatedComputing/2017/papers/ZUI/pad++-uis94-p17-bederson.pdf)). Transitions between levels matter. Heer and Robertson found animated transitions better than static ones. Staged animation came out best, with about 1 to 1.25 seconds in total. They require "semantic correspondence": one mark keeps standing for one item ([Heer & Robertson 2007](https://homes.cs.washington.edu/~jheer/files/2007-AnimatedTrans-InfoVis.pdf)). The evidence for preserving the mental map stays mixed for comprehension. It holds up for **navigation and orientation tasks** ([Archambault & Purchase 2012](https://rd.springer.com/chapter/10.1007/978-3-642-36763-2_42)), and a code map serves exactly those tasks. Jul and Furnas name the failure mode of zoomable views "desert fog": a view with no cues. Their remedy, "residue", shows where zooming in leads to something ([UIST 1998](https://uist.acm.org/archive/html/keywords/kwzone.html)). Shneiderman's History task, "undo, replay, and progressive refinement", completes the set ([Shneiderman 1996](https://www.cs.umd.edu/~ben/papers/Shneiderman1996eyes.pdf)).

## Explanation needs its own layer beside the reference

Diátaxis separates reference, "a close-up of the machinery", from explanation, which takes a "higher, wider view" of history, alternatives and reasons. It titles explanation pages "About [topic]" ([Diátaxis](https://diataxis.fr/explanation/)). A code map works as reference. The reader still wants understanding, so the map needs explanation blocks beside the facts. NN/g warns that designs with **more than 2 disclosure levels** "typically have low usability" ([NN/g](https://www.nngroup.com/articles/progressive-disclosure/)).

Bret Victor locates insight "in the transitions between" levels of abstraction. The reader steps down to a concrete case and steps up to a pattern ([Up and Down the Ladder of Abstraction](https://worrydream.com/LadderOfAbstraction/)). In an explorable explanation, "the author holds up their end of the conversation". Interaction stays optional, and the text reads normally without it ([Explorable Explanations](https://worrydream.com/ExplorableExplanations/)). The Distill review of interactive articles reports better comprehension with step-based (slideshow) layouts. It names unused interactivity and accessibility as the main risks ([Hohman et al. 2020](https://distill.pub/2020/communicating-with-interactive-articles/)). CodeTour gives a working data model for tours ([microsoft/codetour](https://github.com/microsoft/codetour)). A tour holds ordered steps. Each step anchors to a location and carries markdown. Content-only steps can introduce a tour. One "primary" tour greets new developers. The tours live as JSON under version control.

AI code wikis add generated "what this does / how it fits" prose. Every section links to code, and the tools generate architecture and sequence diagrams ([Google Code Wiki](https://developers.googleblog.com/introducing-code-wiki-accelerating-your-code-understanding/); [DeepWiki](https://docs.devin.ai/work-with-devin/deepwiki)). Their weakness lies in trust. Code Wiki carries the warning "Gemini can make mistakes, so double-check it" ([The Register](https://www.theregister.com/2025/11/17/google_previews_code_wiki/)). No source quantifies the accuracy of either product. DeepWiki's steering file, with a title and purpose for each page, points to a hybrid: humans curate region descriptions, and generators fill gaps under a visible "generated" mark. The commercial record carries a caution too. Sourcetrail became an archive in 2021, and GitKraken absorbed CodeSee in 2024 ([GitHub](https://github.com/CoatiSoftware/Sourcetrail); [GitKraken](https://gitkraken.com/press/gitkraken-acquires-codesee-launches-devex-platform)). These events say little about the UI patterns. They do suggest that the map should live beside the docs and code that developers already trust.

## Colour must never carry meaning alone

WCAG 1.4.1 forbids colour as "the only visual means of conveying information". A lightness difference counts as a second cue only at **3:1 contrast or more** ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)). The Okabe–Ito palette gives eight colours that stay distinct under the common forms of colour-vision deficiency. Its main hues: orange #E69F00, sky blue #56B4E9, bluish green #009E73, yellow #F0E442, blue #0072B2, vermillion #D55E00 and reddish purple #CC79A7 ([Jfly](https://jfly.uni-koeln.de/color)). Sourcetrail's yellow-for-calls and blue-for-variables scheme shows the habit of one hue per relation. Hue alone fails the WCAG rule, so the map must add line pattern and a text label.

Keyboard access for networks follows a "browse-then-commit" pattern. Arrow keys cycle through a node's connections. Enter follows a connection. Backspace returns. A separate key switches between incoming and outgoing links ([QUARTZ preprint](https://arxiv.org/pdf/2608.11364); [Data Navigator](https://dig.cmu.edu/data-navigator/)). Practitioner guidance warns that a dense graph gives a poor screen-reader experience. It recommends equivalent value, such as a structured list, over a literal walk of the graph ([Cambridge Intelligence](https://cambridge-intelligence.com/build-accessible-data-visualization-apps-with-keylines/)). A focus view already forms an ego network, so it maps onto this keyboard model with little extra work.

## Concrete changes for the Go documentation map

The evidence above produces the following design changes for a map with three levels (regions, then packages, then types and functions) and four edge kinds (calls, implements, field types, inputs and outputs). Do them in this order. The early steps carry the strongest evidence.

1. **Make focus mode the main work surface.** Select a node. The map redraws only that node and its one-hop relations. Fade out the removed nodes, move the kept nodes, then fade in the new nodes, in about 1.1 s in total. Keep each kept node as the same mark. Under `prefers-reduced-motion`, use a cross-fade.
2. **Use a layered layout with three columns.** Put incoming relations on the left: callers, importers, and types that hold this type as a field. Put the focus in the centre. Put outgoing relations on the right: callees, imports, field types, parameter types and return types. Put implementers or implemented interfaces in a lane below the focus. Put sibling symbols from the same package in a lane above it.
3. **Group each column by relation, under a verb header.** Use these headers: "called by", "calls", "implements", "implemented by", "has field", "takes", "returns". Show a count on each header. One header label replaces many edge labels.
4. **Cap the view at about 20 nodes.** Rank the neighbours by a DOI score: exportedness, fan-in and an author "landmark" flag, minus hop distance. Collapse the rest of each lane into a "+N more" bundle node. Each click on a bundle adds about 5 to 8 nodes. Past about 20 to 50 items in one lane, switch that lane to a grouped list.
5. **Highlight at most 5 "go next" cues.** Show a count of hidden neighbours on every node. Draw short stubs toward hidden endpoints. Blank space must never look like "nothing here".
6. **Hide edges by default outside focus.** At the region and package levels, draw aggregated package-to-package edges. Show each edge's weight as thickness or a count. Let the reader pick which relation kind the map draws.
7. **Redesign each zoom level, and do not only scale it.** A region shows a C4-style card: its name, a one-line purpose, the package count and the main crossings of its border. A package shows a pkgsite-style index: types with their constructors and methods nested under them, plus counts for imports and imported-by. A symbol shows its signature, its first doc sentence, its ego graph and a source link.
8. **Put the first godoc sentence under every name.** This gives scent to terse Go identifiers. Name regions by purpose, and do not name them after directories. Search over identifiers and doc text, with camel-case splitting, and let the search set the focus.
9. **Label every edge with a verb, and keep a legend one click away.** Follow C4: no unlabelled arrows and no "uses". The legend sits behind a `?` button.
10. **Encode each relation three ways.** Use an Okabe–Ito hue, a line pattern (for example solid for calls, dashed for field types, dotted for implements, double-headed for inputs and outputs) and the column's text header. Encode each node kind by shape plus a text tag: "pkg", "T", "I", "fn". Check that strokes reach 3:1 contrast in both themes.
11. **Make the map keyboard-first and give it a parallel list.** Tab enters the graph. Arrow keys move among neighbours. Enter refocuses. Backspace goes back. A key toggles between incoming and outgoing. An `aria-live` region announces lines such as "store.Put, function, 3 callers, 2 callees". An HTML list of the current neighbourhood mirrors the graph for screen readers.
12. **Make every state addressable.** Encode the focus and depth in the URL. Push each refocus to browser history. Show a breadcrumb (region › package › type › method) with sibling dropdowns. A click on a crumb zooms out with the reverse animation. Keep a mini-map inset that marks the current focus.
13. **Add a path mode.** "Path from A to B" finds and draws the call chain between two symbols, as Sourcetrail's To Target Symbol trail does. Show curated request flows (for example handler → service → store) as numbered overlays or sequence diagrams, as Structurizr dynamic views do. Keep the flows out of the static map.
14. **Split the side panel into two disclosure levels.** The always-visible level holds the purpose sentence and the reference facts: signature, file and line link, edge counts and call-site snippets on edge click. The second level holds an "About this package" (or region) block with the why: decisions, constraints, alternatives, and links to the charter, design records and issues that govern the node. Link those records back to the node.
15. **Add guided tours as data.** Store each tour as an ordered list of steps under version control, with a node ID, a title and markdown per step. Each step sets the focus and reuses the focus animation. Start with a content-only overview step. Then follow one concrete request down the map before naming the region-level pattern. End by inviting free exploration. Mark one tour as primary for newcomers.
16. **Let readers build and name working sets.** Readers pin nodes, name the group and add a note on why they look. They save it as a shareable URL. This covers Storey's E3 and E11, which most tools skip.
17. **Mark generated prose.** Show human-curated descriptions first. Label any machine-generated summary as generated.
18. **Keep metrics out of the default encoding.** Use counts as navigation badges only. Do not size nodes by lines of code.

## Conclusion

The research changes the question. A designer should not ask "how do I draw the codebase?" but "which question does this view answer, and what may it omit?" Every durable success in the record narrows the view: one symbol, one path, one level, one tour. Every failure tried to answer all questions at once. For a Go backend, Go itself does much of the work. Godoc first sentences supply scent. pkgsite's index supplies the package layout. Interfaces and constructors act as beacons. The novel work lies in the layer that research marks as least supported: path questions answered by search along calls, rationale linked in both directions to the nodes it governs, and reader-built working sets that record why someone looked.

Three uncertainties should shape any evaluation of the resulting map. First, no controlled study isolates semantic zoom or compares ego views with whole graphs for code. The design rests on transfers from general graph and interactive-article research. Second, the 20-node budget and the 1-second transition come from generic tasks. Tune both against real Go packages with high fan-in. Third, developers "try to avoid program comprehension" and trust code over documentation. Measure adoption by whether a reader answers a reachability or "why" question faster than with the editor and pkg.go.dev alone, and not by whether readers like the map.
