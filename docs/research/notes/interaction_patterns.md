# Interaction design and explanatory-writing patterns for an interactive Go code map with a focus mode

Scope: design guidance for a zoomable code map (regions, then packages, then types and functions) with a "focus mode" that redraws the map with only the selected item and its relationships, plus guidance on writing the explanations beside it. Primary sources were read where they could be reached. van Ham & Perer 2009, Heer & Robertson 2007 and Shneiderman 1996 were read in full text with pdftotext. Some other items rest on secondary summaries, and the notes say which.

## 1. Focus+context, semantic zoom, and degree-of-interest: how should a focus view choose neighbours, and how many nodes is too many?

### Takeaway
Use a degree-of-interest (DOI) score, made of a-priori importance, distance from the focus and (optionally) the search or user context, to select a **connected subgraph of a fixed budget S** around the focus. Show the count of hidden neighbours on each node and cue at most about 5 of the "most interesting" directions to expand. Expand in increments of the top N, never "all neighbours". Node-link diagrams read best at roughly 20 nodes or fewer (the Ghoniem et al. result), and the advantage shrinks by about 50. So a focus view should aim for roughly 15 to 30 visible nodes and aggregate the rest.

### Cited Findings
- Shneiderman's Visual Information-Seeking Mantra is "Overview first, zoom and filter, then details-on-demand". His seven tasks are Overview, Zoom, Filter, Details-on-demand, Relate ("View relationships among items"), History ("Keep a history of actions to support undo, replay, and progressive refinement") and Extract — [Shneiderman 1996, The Eyes Have It](https://www.cs.umd.edu/~ben/papers/Shneiderman1996eyes.pdf)
- Shneiderman: "Smooth zooming helps users preserve their sense of position and context". Dynamic-query filters should update the display in "less than 100 milliseconds". Details-on-demand applies "once a collection has been trimmed to a few dozen items". Overview+detail with a field-of-view box gives zoom factors of 3 to 30, and fisheye prototypes are "limited to about 5" — [Shneiderman 1996](https://www.cs.umd.edu/~ben/papers/Shneiderman1996eyes.pdf)
- Furnas's DOI, as van Ham & Perer restate it, has two parts: an a-priori interest API(x) "irrespective of the user's current interest" and a distance D(x,y) from the focus y, combined as DOI(x|y) = α·API(x) + β·D(x,y). "By effectively eliding nodes below a certain interest threshold" one gets compact displays of very large structures — [van Ham & Perer 2009, IEEE TVCG 15(6)](https://perer.org/papers/adamPerer-DOIGraphs-InfoVis2009.pdf)
- For general graphs, API can come from "structural graph properties or node attributes, such as node degree". D is the graph distance, weighted by a per-edge disinterest function EI(e,x,y) > 0, which lets some edge types count as "farther" than others — [van Ham & Perer 2009](https://perer.org/papers/adamPerer-DOIGraphs-InfoVis2009.pdf)
- They add a User Interest term from the search that led to the focus: DOI(x|y,z) = α·APIdiff(x) + β·UIdiff(x,z) + γ·D(x,y). Interest is diffused to neighbours with a factor δ (0 ≤ δ < 1), so that a greedy search can reach high-interest nodes that sit behind low-interest ones. Plain thresholding on graphs gives disconnected pieces — [van Ham & Perer 2009](https://perer.org/papers/adamPerer-DOIGraphs-InfoVis2009.pdf)
- "Show Context": compute "a connected subgraph F of size at most S that contains y and has maximal total interest". The greedy method starts from {y}, repeatedly adds the highest-DOI candidate and pushes its neighbours onto a heap, in O(S log S) — [van Ham & Perer 2009](https://perer.org/papers/adamPerer-DOIGraphs-InfoVis2009.pdf)
- "Expand on demand": adding all neighbours of a clicked node risks "hundreds of nodes resulting in potentially unreadable graphs". So add only the "top N most interesting" nodes, and each further click brings N more. Label "the number of neighbors on each node" — [van Ham & Perer 2009](https://perer.org/papers/adamPerer-DOIGraphs-InfoVis2009.pdf)
- Guide the next step: "visually highlight the n most interesting directions for expansion. Typically, n should be small (n<5) to avoid overloading the user with choices" — [van Ham & Perer 2009](https://perer.org/papers/adamPerer-DOIGraphs-InfoVis2009.pdf)
- Hidden connections are drawn as short "fading edges" that point toward the hidden endpoint's layout position, with a cap per node and the exact count shown on the node. After an expansion, "a new layout is computed based on the initial layout and the whole graph is then smoothly animated to its new position". The layout uses stress majorization rather than gradient-descent force layout, for "far better layout stability" — [van Ham & Perer 2009](https://perer.org/papers/adamPerer-DOIGraphs-InfoVis2009.pdf)
- Scale example: without DOI, all cases two hops from one focus came to 2,345 nodes and 2,847 edges, "impractical to visualize using a node link diagram" — [van Ham & Perer 2009](https://perer.org/papers/adamPerer-DOIGraphs-InfoVis2009.pdf)
- Semantic zooming in Pad++: "When you zoom out, you see a simplified rendering of the object". Rendering "can be based on various semantic and task considerations", so it is not merely geometric scaling — [Bederson et al., CHI '95 Pad++ demo](https://chi1995.chistatic.hosting.acm.org/proceedings/demos/pad_bdy.htm); [Bederson & Hollan, UIST '94](https://www.lri.fr/~mbl/Teach/SituatedComputing/2017/papers/ZUI/pad++-uis94-p17-bederson.pdf) (excerpts via search, full text not read)
- Readability limits: Ghoniem, Fekete & Castagliola (2004) tested 20-, 50- and 100-node graphs. They report that above about 20 vertices, matrices beat node-link diagrams on most tasks, except path finding, which consistently favours node-link — summarised in [Okoe, Jianu & Kobourov, TVCG 2018](https://smsf.cs.arizona.edu/~kobourov/NL-AM-TVCG18.pdf) (original abstract via search). Okoe et al. found node-link more accurate in 5 of 10 tasks and less accurate in 2 — same source. Ren et al. found node-link best on 20- and 50-node networks, with the advantage "attenuated in the larger (50-node) network" — [Ren et al., Network Science](https://www.cambridge.org/core/journals/network-science/article/understanding-nodelink-and-matrix-visualizations-of-networks-a-largescale-online-experiment/C293136C4761F09D4C2C328E2BC19287)

### Inferences
- For a Go code map: API(x) can be exportedness, fan-in (how many packages import it or call it), or a "landmark" flag set by the author. D is the hop count. EI can make "implements" and "calls" edges cheaper to follow than "same file". UI can be the search term or the region the user came from.
- Focus-mode budget: about 20 nodes in the first view (the Ghoniem threshold), expandable in steps of N of about 5 to 8, with at most about 5 highlighted "go here next" cues. Show a "+37" badge on nodes whose neighbours are hidden, rather than drawing them.
- Semantic zoom maps directly onto the three levels. A region shows a name, a one-line purpose and a package count. A package shows its exported types and its key imports. A type or function shows its signature, methods and callers. Each level should be redesigned, not only scaled.
- Path-finding questions ("how does a request get from handler to store?") favour node-link. Dense "who depends on whom" questions at the package level may be better served by a matrix or a list fallback.

### Gaps
- I found no source that gives an empirically optimal node count for ego-network focus views. The 20-node figure comes from general node-link vs matrix tasks.
- Furnas 1986 "Generalized Fisheye Views" (original form DOI = API − D) was not read directly. Its formula is taken from van Ham & Perer's restatement.

## 2. Ego-network layouts, edge grouping and bundling, labelled edges, and transitions that keep the mental map

### Takeaway
For a focus view with directed relations, a layered left-to-right layout (callers and importers to the left, the focus in the centre, callees and imports to the right), grouped by edge type, is easier to read and to keep stable than a force layout. Animate the change from overview to focus in about 1 second (Heer & Robertson tested 1.25 s), staged: first fade out the removed nodes, then move the kept nodes, then fade in the new ones. Keep surviving nodes as the same marks. Evidence that "mental map" stability helps is mixed, but it helps orientation and navigation tasks.

### Cited Findings
- Heer & Robertson's guidelines, under Congruence: "Maintain valid data graphics during transitions", "Use consistent semantic-syntactic mappings" (the same operation gets the same animation everywhere), and "Respect semantic correspondence" (a mark that stands for one item must not be reused for a different item). Under Apprehension: "Group similar transitions" (common fate), "Minimize occlusion", "Maximize predictability" (slow-in slow-out), "Use simple transitions" (translation and expand/contract are easier than rotation), "Use staging for complex transitions", and "Make transitions as long as needed, but no longer" — [Heer & Robertson 2007, IEEE TVCG 13(6)](https://homes.cs.washington.edu/~jheer/files/2007-AnimatedTrans-InfoVis.pdf)
- Timing: Robertson et al.'s results "recommend transition times around 1 second". The experiments used 1.25-second animated transitions. Earlier work found "Simple transitions (e.g., translation rather than rotation) about 1 second long gave the best performance" — [Heer & Robertson 2007](https://homes.cs.washington.edu/~jheer/files/2007-AnimatedTrans-InfoVis.pdf)
- Results: animation was significantly better than static transitions across conditions in Experiment 1. Staged animation mostly outperformed unstaged animation, and in the preference survey "staged animation is preferred to animation, which is preferred to static transitions". Occlusion "sometimes complicated object tracking, particularly when three or more items overlapped", which they handled by staggering start times. Filtered items enter and exit by alpha blending — [Heer & Robertson 2007](https://homes.cs.washington.edu/~jheer/files/2007-AnimatedTrans-InfoVis.pdf)
- Related evidence they cite: Bederson & Boltman found that animated transitions in a family-tree explorer improved the ability to reconstruct the tree from memory. Robertson et al. found that animation improved task time and satisfaction in polyarchy visualisations — [Heer & Robertson 2007](https://homes.cs.washington.edu/~jheer/files/2007-AnimatedTrans-InfoVis.pdf)
- van Ham & Perer compute each new layout from the previous one and animate to it, and they use stress majorization for stability — [van Ham & Perer 2009](https://perer.org/papers/adamPerer-DOIGraphs-InfoVis2009.pdf)
- Mental-map evidence is mixed. Archambault et al. (TVCG 2011) found that preserving the mental map had little effect on errors or time for comprehension tasks — [Monash record](https://research.monash.edu/en/publications/animation-small-multiples-and-the-effect-of-mental-map-preservati/). Archambault & Purchase (GD 2012) found that preservation gave faster, more accurate results for navigation and orientation tasks, and called it the first formal experiment to show a benefit — [Springer](https://rd.springer.com/chapter/10.1007/978-3-642-36763-2_42). A 2013 IJHCS review says no experiment has given conclusive evidence for comprehension — [Monash record](https://research.monash.edu/en/publications/the-map-in-the-mental-map-experimental-results-in-dynamic-graph-d/) (abstracts only)
- Hierarchical edge bundling (Holten 2006) routes adjacency edges along the containment hierarchy, which reduces clutter and shows implicit edges between parent groups. A strength parameter trades node-to-node detail against group-level structure. The method has been applied to software dependency graphs — [Holten 2006, TVCG 12(5)](https://research.tue.nl/nl/publications/hierarchical-edge-bundles-visualization-of-adjacency-relations-in/); [Telea, software dependencies](https://webspace.science.uu.nl/~telea001/SoftVis/Dependencies) (via search; no quantitative evaluation found)
- TreePlus showed graphs as an enhanced tree layout, "which users often find more comprehensible than a graph layout". Ego-centric tools "struggle with very high degree nodes" — [van Ham & Perer 2009, related work](https://perer.org/papers/adamPerer-DOIGraphs-InfoVis2009.pdf)

### Inferences
- Recommended focus layout: three columns. Incoming relations (importers and callers) go on the left, the focus in the centre, outgoing relations (imports and callees) on the right. Implementations of an interface can go below and siblings in the same package above. Inside each column, group by edge type under a small header ("calls", "implements", "embeds"), so that one label per group replaces one label per edge. This is the TreePlus-style "tree is easier" idea applied in both directions.
- When a column has more than about 7 items, collapse the rest into a "+N more" node. That is consistent with expand-by-N.
- Bundle edges by their parent package or region when a column shows items from the same package, following Holten's idea at a small scale.
- Transition when entering focus: (1) fade out the nodes that are not kept, at about 300 ms, (2) translate the kept nodes, the focus included, to their new positions, at about 500 ms, (3) fade in the new neighbours and edges, at about 300 ms. That totals about 1.1 s. Respect prefers-reduced-motion by cross-fading instead. The stage lengths are my inference from the 1 s to 1.25 s guidance; the papers give no per-stage numbers.
- Keep node identity across zoom levels: the same package box grows into the focus, rather than vanishing and reappearing (semantic correspondence).

### Gaps
- I found no controlled study that compares radial and layered ego layouts for directed code relations. The layered recommendation is inferred from the direction semantics and from the TreePlus remark.

## 3. Navigation history, breadcrumbs, back and forward, and "where am I" orientation (desert fog)

### Takeaway
Zoomable interfaces need explicit orientation cues. Jul & Furnas name "desert fog", a view with no navigational cues, and propose "residue": signs that show where zooming in will lead to something. Pair this with Shneiderman's History task: give each focus state a URL, support browser back and forward, show a breadcrumb (Region › Package › Type), and keep a small overview inset that marks the current focus.

### Cited Findings
- Jul & Furnas, "Critical Zones in Desert Fog: Aids to Multiscale Navigation", UIST 1998, pp. 97–106. Its keywords include residue, view-navigation and space-scale diagram — [UIST archive](https://uist.acm.org/archive/html/keywords/kwzone.html)
- Desert fog is "the frequent lack of informational cues to aid their continued search" in multiscale views — [ICA abstract 2025 citing Jul & Furnas](https://ica-abs.copernicus.org/articles/10/173/2025/ica-abs-10-173-2025.pdf). A critical zone is a region where zooming in leads to interesting views, signalled by navigation "residue" — [UBC CPSC 533 slides](https://www.cs.ubc.ca/~tmm/courses/cs533c-02/0312.week9/mgp00016.txt) (secondary)
- Shneiderman's History task: "Keep a history of actions to support undo, replay, and progressive refinement" — [Shneiderman 1996](https://www.cs.umd.edu/~ben/papers/Shneiderman1996eyes.pdf)
- Overview+detail: an overview with "a movable field-of-view box to control the contents of the detail view" — [Shneiderman 1996](https://www.cs.umd.edu/~ben/papers/Shneiderman1996eyes.pdf)
- van Ham & Perer start every exploration with Search (a text search, faceted search, or a visual search such as a scatterplot), because without an overview users must find a focus first. Other search matches stay highlighted in the focus view — [van Ham & Perer 2009](https://perer.org/papers/adamPerer-DOIGraphs-InfoVis2009.pdf)
- Background reading on navigation in multiscale space: Furnas & Bederson "Space-Scale Diagrams" (CHI '95), and van Wijk & Nuij "Smooth and Efficient Zooming and Panning" (InfoVis 2003), which gives optimal zoom-pan paths — [UBC nav slides, reading list](https://www.cs.ubc.ca/~tmm/courses/533-09/slides/nav.pdf)

### Inferences
- Residue for the code map: show child counts and a sketch of the content (small dots or a package-count badge) on each region or package, so that empty space never looks the same as "nothing here". The fading-edge stubs and "+N" counts in focus mode are the same idea.
- Make every focus state addressable (for example `#focus=pkg/store&depth=1`) and push it to history, so that the browser Back button undoes a focus. Shneiderman's "replay" is covered by shareable URLs.
- The breadcrumb doubles as zoom-out: clicking "Region" in Region › Package › Type steps up one level with the reverse animation.
- Keep a persistent mini-map or overview inset that shows the whole map with the current focus highlighted. This is overview+detail, and it is the direct remedy for desert fog.
- Search is the main way into the map (van Ham & Perer), so give it a prominent search box that sets the focus.

### Gaps
- I could not reach the full text of Jul & Furnas 1998. Their experimental findings and their exact taxonomy of residue are not verified here.
- No primary source was found with numeric guidance on breadcrumb depth or the size of a history stack.

## 4. Explanatory writing: Diátaxis mode, progressive disclosure, explorable explanations, interactive articles, and guided code tours

### Takeaway
A code map is reference (a close-up of the machinery), but the user wants understanding, which is Diátaxis "explanation". Keep the two apart. Put the map and the per-node facts (signature, file, edges) in reference panels. Write separate "About X" explanation blocks that give the why: the design decisions, constraints and alternatives. Use at most 2 disclosure levels per panel. Add an author-led guided tour (CodeTour style: ordered steps, each anchored to a node, with markdown text, next and previous, and one primary tour) that walks up and down the ladder of abstraction, from a concrete request path to the region-level pattern.

### Cited Findings
- Diátaxis explanation is "understanding-oriented" and answers "Can you tell me about...?". Reference gives a close-up of the machinery. Explanation takes a "higher, wider view", covering history, alternatives and reasons, and may unfold internals "to help understand why something does what it does" — [Diátaxis: Explanation](https://diataxis.fr/explanation/)
- Diátaxis writing rules for explanation: make connections, including to things outside the topic; give context (design decisions, history, constraints); title it "About [topic]"; admit opinion and weigh alternatives; keep it tightly bounded, with no instructions or detailed technical description, since "explanation is required to form that web that helps hold everything together" — [Diátaxis: Explanation](https://diataxis.fr/explanation/)
- Progressive disclosure: "designs that go beyond 2 disclosure levels typically have low usability". Show frequent items first. Make the control that discloses more visible and clearly labelled. Staged disclosure suits linear tasks but is "problematic when the steps are interdependent" — [NN/g, Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)
- Bret Victor: "the most powerful way to gain insight into a system is by moving between levels of abstraction". Step up by abstracting over a variable to see patterns ("The purpose of abstraction is to bring out high-level patterns"). Step down by picking a concrete point from the abstraction. The insight is "in the transitions between them" — [Victor, Up and Down the Ladder of Abstraction](https://worrydream.com/LadderOfAbstraction/)
- Explorable explanations: an explorable text still reads normally, and interaction is optional. "the author holds up their end of the conversation", because interactivity without structure is not an explanation. Models and assumptions are visible. Contextual information is brought to the reader in place — [Victor, Explorable Explanations](https://worrydream.com/ExplorableExplanations/)
- Distill "Communicating with Interactive Articles": details-on-demand with an overview kept visible, and previews such as hover cards that avoid a page change. Use prediction prompts ("You Draw It") and low-stakes quizzes. Segment content into pieces readers can pace. Evidence on layout: McKenna et al. found readers preferred step or scroll layouts to static ones, but engagement did not differ; Zhi et al. found better comprehension with slideshow (step) layouts. Risks: interactivity that goes unused or distracts, and accessibility, which is called an open problem — [Hohman et al., Distill 2020](https://distill.pub/2020/communicating-with-interactive-articles/)
- Distill cites the Multimedia Principle: people learn better from "words and pictures rather than words or pictures alone" — [Distill 2020](https://distill.pub/2020/communicating-with-interactive-articles/)
- CodeTour: a tour is "a series of interactive steps, each of which are associated with a specific directory, or file/line". It supports content-only steps (a title and markdown, with no file) for introductions, markdown with links to other steps and tours, Move Previous and Move Next (Ctrl or Cmd plus arrow keys), resume, a "primary" tour shown first to new developers, numbered tours linked by Next Tour and Previous Tour, and tours stored as JSON in `.tours/` under version control — [microsoft/codetour](https://github.com/microsoft/codetour)

### Inferences
- Panel structure per node: (a) a one-sentence purpose, always visible; (b) a reference facts block (signature, file:line link, counts of edges in and out); (c) an "About this package" explanation, collapsed or below the fold. That is two disclosure levels, not three.
- Write explanations at the level of the zoom. A region explains why the region exists and what crosses its border. A package explains its responsibility, its main types and the decisions behind them. A function explains its role in a flow. Each one links up ("part of the storage region") and down ("start with `Store.Put`"), so the reader moves along Victor's ladder.
- Guided tours as data: an ordered list of {nodeId, title, markdown} steps. Each step sets the focus mode, which reuses the focus transition. A step-based layout fits the Zhi et al. comprehension evidence. Begin with a content-only overview step and end with a pointer to free exploration.
- Ground abstractions in a concrete trace, for example "follow one HTTP request", before showing region-level patterns. That is stepping down the ladder first, then stepping up.
- Optional "predict first" prompts ("Which packages do you think call the store?" before the reveal) apply the Distill self-explanation evidence. Use them sparingly.
- Name the explanation blocks "About …", following the Diátaxis convention, so readers can tell the why from the facts.

### Gaps
- No controlled studies were found on code-map documentation specifically. The guidance is transferred from general interactive-article and documentation research.

## 5. Accessibility: colour-blind-safe encoding, redundant encoding, and keyboard navigation of graphs

### Takeaway
Never encode edge or node type by hue alone (WCAG 1.4.1). Pair colour with dash pattern, arrowhead or shape, and a text label. Use a colour-blind-safe palette such as Okabe–Ito, and avoid red/green pairs. For keyboard use, follow the "browse-then-commit" model: arrow keys cycle through a node's neighbours, Enter makes the selected neighbour the focus, Backspace or Escape goes back, and a key toggles incoming and outgoing. Give a text or list alternative of the focus neighbourhood for screen readers.

### Cited Findings
- WCAG 1.4.1 (Level A): "Color is not used as the only visual means of conveying information". A lightness difference counts as a second cue only at a contrast of "3:1 or greater". Technique G111 uses colour and pattern, G14 makes the colour information also available in text, and failure F13 is a chart that conveys information only by colour — [W3C Understanding 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)
- The Okabe–Ito palette: #E69F00 orange, #56B4E9 sky blue, #009E73 bluish green, #F0E442 yellow, #0072B2 blue, #D55E00 vermillion, #CC79A7 reddish purple, plus black or #999999 grey. Okabe and Ito's aim is colours distinguishable to all viewers, including colour-blind ones — [Jfly, Color Universal Design](https://jfly.uni-koeln.de/color); hex values from [colorblindr source](https://rdrr.io/github/clauswilke/colorblindr/src/R/palettes.R) (third-party implementation)
- Keyboard model for networks (QUARTZ): arrow keys cycle through a node's connections, Enter follows a connection, Backspace returns to the previous node, and a separate key switches between outgoing and incoming links — [QUARTZ, arXiv 2608.11364](https://arxiv.org/pdf/2608.11364) (via search summary)
- CMU Data Navigator is a library for "keyboard, screen reader, and multi-modal navigation" of structures that include networks, with custom keys for moving along edges and leaving a structure — [Data Navigator](https://dig.cmu.edu/data-navigator/); [paper](https://arxiv.org/pdf/2308.08475)
- Linkurious Ogma's accessibility example has three modes: a menu mode (Tab and arrow keys), a graph mode (arrow keys and Enter to move along edges) and a camera mode (a crosshair) — [Ogma accessibility example](https://doc.linkurious.com/ogma/latest/examples/accessibility.html)
- Practitioner guidance: add keyboard navigation and text alternatives first, then ARIA labels for the structure. A dense graph is a poor screen-reader experience, so aim for equivalent value rather than a literal walk of the graph — [Cambridge Intelligence](https://cambridge-intelligence.com/build-accessible-data-visualization-apps-with-keylines/); [Neo4j](https://neo4j.com/?p=444940) (vendor sources)

### Inferences
- Edge-type encoding: solid line for calls, dashed for imports, dotted for implements, double or hollow arrowhead for embeds. Each type also gets an Okabe–Ito hue and a group header label in the focus columns. The meaning then survives greyscale and every type of colour vision deficiency.
- Node kinds: shape plus a text tag, for example a rounded rectangle for a package, a rectangle with "T" for a type, and an ellipse with "fn" for a function.
- Focus mode is an ego network, so it maps directly onto browse-then-commit. Tab enters the graph, arrow keys move among neighbours (grouped incoming then outgoing), Enter refocuses (push to history), and Backspace goes back. An `aria-live` region announces "store.Put, function, 3 callers, 2 callees".
- Give a parallel HTML list of the current focus neighbourhood (grouped by direction and type, with links that refocus), so screen-reader users get the same information without walking an SVG.
- Honour prefers-reduced-motion for the section 2 transitions, and keep strokes and markers at 3:1 non-text contrast against the background in both themes.

### Gaps
- WCAG 1.4.11 (Non-text Contrast, 3:1) was not fetched directly. Its 3:1 threshold is stated from general knowledge and from the 1.4.1 page's lightness rule.
- The QUARTZ details come from a search summary of a 2026 arXiv preprint, not a full read.
- I did not verify the Okabe–Ito hex values against the original Jfly page.
